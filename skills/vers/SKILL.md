# VERS — Verification Engine for Rust Systems

Treat code and the implementer's claims as untrusted. Compiling, linting, and passing tests do not by themselves establish correctness. Report evidence, failures, and missing coverage separately; never turn BLOCKED into PASS or invent a finding or result. VERS v0.2 can incorporate documented independent reviews when the operator has verified their provenance. The tool cannot authenticate reviewer identity, enforce independence, or judge review quality; do not invent evidence or claim those guarantees.

## Routing and execution

`$vers` selects this skill in hosts that install and discover it; text after the skill name is a request to the agent, not an automatically parsed CLI command. The agent maps `--diff`, `--full`, or `--strict` to the same flag of `scripts/verify.sh`; `--report` displays the latest report, or `--report PATH` displays a specified report. `--diff` currently runs the workspace checks rather than computing a reduced scope; `--strict` records additional coverage as BLOCKED. Do not claim these modes implement more than that.

1. Identify the candidate, requirements, acceptance contracts, scope, toolchain, Git HEAD and dirty/untracked files. Inspect CI, feature and target choices, `build.rs`, procedural macros, FFI, subprocesses, generated code, and tests that use networks or external systems. Do not execute project code during discovery. Note untrusted code may execute during Cargo commands.
2. Decide whether execution is authorized and safe. The harness copies source but does **not** sandbox build scripts, runtime commands, filesystem access, network access, or resource consumption. For untrusted projects use an appropriate isolated environment with no production credentials, network or dangerous host access; otherwise do not execute. Never run destructive or production-facing tests without explicit authorization and isolation.
3. Configure explicit, independently derived runtime cases and run `scripts/verify.sh --root /path/to/workspace --execute` from the appropriate isolation. `--execute` signifies a deliberate trust/isolation decision. Without it commands are BLOCKED. The harness expects a Git-root workspace, `timeout`, Rust and locally cached dependencies. Exit 0 means PASS, 1 FAIL, 2 BLOCKED or infrastructure/config error; use JSON, not the exit code alone, to distinguish the last two. Logs can contain secrets; inspect and sanitize before sharing.
4. Review the actual candidate independently. Read [rust-safety.md](references/rust-safety.md) for G2, [review-rubric.md](references/review-rubric.md) for G3–G5 and iteration, and [runtime-contracts.md](references/runtime-contracts.md) for G6 and configuration. Run applicable project-specific feature, target, release, Miri and security checks when available. Record command, exit, evidence and limitations. Not applicable conditional checks need a rationale; unavailable mandatory checks are BLOCKED. Follow [review-evidence.md](references/review-evidence.md) to prepare protected review records and rerun the harness. Use `--trust-reviews` only after the operator has verified their provenance and independence; names in a policy are not authentication.
5. Report the candidate identity and dirty state, exact commands, toolchain, evidence, reproducible findings with file/line and severity when known, uncovered risks, and next action. A FAIL is an observed mandatory failure; BLOCKED means verification was incomplete. Report both failures and blocked checks. Treat the identity as invalid if inputs change; verify every repair as a new candidate.

## Recover from a block

For each blocked check or infrastructure error, identify its cause, the missing prerequisite or evidence, and the action and conditions needed to retry. Record observed failures as well as blocks. Investigate and resolve verification prerequisites within the authorized scope, such as locating an available tool, preparing independently derived runtime contracts, or arranging qualifying review evidence. Do not change the candidate by default: hand candidate changes and reproducible defects to the implementer or user. Configuration changes inside the candidate change its identity and require fresh applicable verification and reviews.

Continue useful authorized work that does not depend on the blocked gate. Retry affected checks only after a relevant prerequisite, candidate, or evidence changes; re-identify the candidate and report the new result. If an independent reviewer, protected evidence, operator attestation, permission, or other external dependency is unavailable, report what is needed and leave the dependent checks BLOCKED. Do not represent self-review as independent, attest unverified provenance, waive requested strict coverage, or rerun an unchanged block without a reason. Stop the affected attempt when no authorized action can make measurable progress or the agreed resource budget is reached.

Offer reproducible failures and proposed repairs to the implementing agent, or the user if no separate agent is available. Never spawn an agent without host authorization. Keep verification instructions and reports outside the implementer's control when independence matters; do not merge, deploy, or publish.

See [integration.md](references/integration.md) for installation, report semantics, isolation limits, and harness tests. The schema is [report.schema.json](schemas/report.schema.json). Executable examples live in `examples/`; copy and adapt contracts to the project rather than treating examples as evidence.
