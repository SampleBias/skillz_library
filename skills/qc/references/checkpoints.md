# Checkpoints, pause, and resume

A checkpoint may be recommended after an accepted milestone, before a major high-risk change, or after a project-agreed work limit. A GitHub push is not automatically authorized by this recommendation. Unless the user or project has already authorized the action, prepare a concrete reviewable checkpoint and ask for the necessary human approval. Do not send messages, commit, push, or use a remote without the applicable authorization and available tooling.

Persist a durable checkpoint in `.qc/reports/` under the external trusted evidence root, using a unique ID and atomic replacement (write a complete temporary file in the same directory, flush as appropriate, then rename; report errors). Never claim durability if persistence fails. Do not treat a JSON report or this skill as an enforced pause controller. Tell the user to avoid further changes while paused, and stop work that would advance the project until explicitly authorized.

Record the milestone and requirements, completed and outstanding tasks, accepted file paths and SHA-256 hashes, candidate snapshot identity and dirty/untracked state, VERS reports and their identities, QC score and report, findings, branch, HEAD, intended remote/ref, intended commit when known, current state, approvals, and next action. Do not record credentials. A push only contains committed work: enumerate dirty and untracked files and ensure all in-scope work is preserved in an explicitly identified commit or a separately durable, verifiable snapshot. A local untracked or temporary report alone is not durable repository storage.

For an approved push workflow, distinguish `AWAITING_PUSH_APPROVAL` (approval or user action still required) and `AWAITING_PUSH_CONFIRMATION` (push authorized or requested, outcome not yet verified). In either state pause project development. If the user performs the push, ask for the branch and commit if not already known. Verify local HEAD, branch, clean or explicitly accounted-for state, accepted hashes, evidence freshness, and the expected remote/ref SHA using read-only Git or an authorized connected service when available. The expected commit must contain the reviewed content; a later remote tip is sufficient only when ancestry and relevant content are verified. If access is unavailable, ref or content differs, in-scope work is uncommitted, or evidence is stale, record `PAUSED`, describe the unresolved condition and do not assert remote verification. A user's push confirmation is not proof of remote state.

After verification, save the result and remain paused until the user explicitly authorizes resumption. On resume, reload the checkpoint, verify saved candidate and repository state and relevant evidence, and compare actual work to the recorded next action. Changes invalidate affected acceptance and require fresh verification. Record the authorization, resume the applicable state and continue only within its scope. Do not manufacture a checkpoint, push, approval, or resume confirmation.

Normal flow is `IMPLEMENTING` → `VERIFYING` → `QC_REVIEW` → `REPAIR` or `ACCEPTED_MILESTONE`; repairs return to verification. Accepted milestones may continue implementing or enter a checkpoint. `READY_FOR_HUMAN_TESTING` and `AWAITING_HUMAN_TEST` require integrated acceptance, while `COMPLETE` requires explicit human sign-off. `PAUSED` can hold any unresolved or user-requested pause. Record the previous state and resumption conditions; do not skip required states or checks merely because a state label exists. The illustrative [checkpoint](../examples/checkpoint.example.json) is fictional, not evidence.
