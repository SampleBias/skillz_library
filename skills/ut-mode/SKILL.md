# UT_MODE — Rust development orchestrator

Carry the user's authorized Rust task from requirements through implementation, verification, repair, and the applicable QC decision. `$ut-mode` is the Codex-compatible skill name for UT_MODE. It coordinates the other skills; it is not a program, autonomous background service, or authority to override their gates or the user's instructions. The other skills remain independently usable.

## Load the team

Locate `patrs`, `amark`, `vers`, and `qc` in the host's available skill catalog and read each installed `SKILL.md` and the supporting references needed for its stage. In a checkout of this library they are sibling directories under `skills/`; when installed separately, use their actual catalog locations instead of assuming a common parent. Apply their instructions to the same task, in sequence, without assuming that writing a skill name automatically executes a separate agent. `packet` is optional: use it when a prompt or structured handoff would help, particularly if the user requests PACKET; it is not a prerequisite for Rust work.

If a required skill or needed tool is unavailable, say what is missing, do any useful authorized work that does not depend on it, and mark the dependent stage and acceptance as BLOCKED. Never invent a result or silently substitute another process for a required gate. See [integration.md](references/integration.md) for installation and realistic handoffs.

## Work loop

1. **Frame.** Inspect project instructions, existing code, scope, requirements, constraints, repository state, Rust toolchain, targets, features, tests, and environment. Identify acceptance criteria, candidate identity, risks, and applicable checks; split substantial work into coherent milestones. Make reasonable assumptions, state material ones, and ask only when an answer is necessary to proceed. Respect the user's desired scope and existing work.
2. **Implement and annotate.** Apply PATRS to the smallest cohesive change, with meaningful tests for behavior and invariants where appropriate. Apply AMARK to the changed code: preserve required safety and API documentation and correct obsolete or unnecessary comments. Run the applicable development checks in the project's actual configuration when execution is authorized and appropriate. Record exact commands, outcomes, and unavailable checks.
3. **Verify.** Identify the actual candidate, including dirty and untracked inputs, requirements, relevant configuration, and external inputs. Apply VERS to that candidate and assess the trust and isolation of every executable check. Prefer a genuinely independent verifier when the host permits and the user has authorized delegation; otherwise perform the available review, label its lack of independence, and leave any independent-verification requirement BLOCKED. Do not spawn agents without authorization. Report VERS PASS, FAIL, and BLOCKED exactly as evidenced; do not upgrade its verdict. When qualifying independent reviews exist, follow VERS review-evidence guidance and have an authorized operator validate provenance before using its trust flag. See [integration.md](references/integration.md) for limits.
4. **Evaluate.** Apply QC to the unchanged candidate and actual evidence. It decides file and integrated milestone acceptance separately, including mandatory gates, scoring, findings, and limitations. Do not average file scores into project acceptance, treat a high score as a mandatory pass, or invent a human sign-off. Keep QC reports in its external evidence root so they do not alter VERS's candidate snapshot.
5. **Diagnose, resolve, and reverify.** For each failure or block, identify its cause, affected gate, missing prerequisite or evidence, and action needed to proceed; record failures and blocks together. Route demonstrated Rust defects to PATRS for root-cause repair and reapply AMARK when relevant. Resolve authorized verification prerequisites, such as missing tools, contracts, or review evidence, without weakening requirements or inventing independence. Continue useful authorized work that does not depend on the blocked gate. After a relevant prerequisite, candidate, or evidence changes, re-identify the candidate, rerun affected checks and VERS, and reassess QC with fresh applicable evidence. An edit or relevant input change invalidates affected evidence and acceptance. Do not repeat an unchanged blocked check without a reason. When no authorized action can make measurable progress or the agreed resource budget is reached, preserve the block, findings, required dependency, and next action rather than looping indefinitely.
6. **Handoff.** When QC gates pass, follow QC's checkpoint and human-testing process as applicable. A requested or configured checkpoint is a hold; preserve the state and resume only under QC's recorded conditions and explicit authorization. `READY_FOR_HUMAN_TESTING` requires integrated acceptance and a reproducible procedure. `COMPLETE` requires human results and explicit final sign-off. Report the actual achieved state, changes, commands/results, evidence, remaining risks, and next action.

A blocked gate does not prohibit other authorized work that does not depend on its acceptance; do not advance a dependent milestone, test handoff, or completion claim. Do not commit, push, deploy, publish, or take other external actions without the authorization required for that action. Do not imply durable pause enforcement, independent verification, remote checks, or human approval that did not occur.
